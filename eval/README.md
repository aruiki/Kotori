# 評価

`just eval` で辞書を作り、評価セットを取得して一括評価する(docs/SPEC.md 14.1、REQ-14-1)。
結果は `eval/results/report.json`(全問の上位候補と順位を含む)と `report.md`(表)に出る。

`just eval-lm` は、ラティスの上位 16 件(REQ-6-1 の K)を zenz-v2.5-small でリランクして評価する
(6.2 モード A)。モデルは先に `just zenz` で用意する(docs/adr/0007)。重みはモデルのメタデータ
`kotori.score_weights` から読み、`kotori-eval run --score-weights <JSON>` で差し替えられる。
結果は `eval/results-lm/` に出る。

`just bench-lm` は、REQ-6-1 の条件でリランク1回の遅延(p50、p95、p99、最大)を測る。AJIMEE-Bench の
読みが 20 文字以上の問題から、読みの先頭 20 文字・左文脈の末尾 64 文字・ラティスの上位 K 件で要求を
作り、各要求を 5 回採点する(最初の1巡は計測しない)。

`kotori-eval tune [--k <件数>] <辞書> <GGUF> <開発用データ>` は、スコア統合の重み(6.2)を格子探索し、
Acc@1 が最大の重みを JSON で出す。λ_lm = 1、T = 1000 に固定し、λ_lattice を探す(順位は
λ_lattice / T だけで決まる)。重みは開発用データで調整し、評価セットでは調整しない(7.3)。
開発用データの用意はメンテナの判断待ち。

| ファイル | 中身 |
| --- | --- |
| `fetch.sh` | 評価セットを固定したコミットから取得し、SHA-256 を検証する。生データは `eval/data/` に置き、コミットしない |

### kotori-heldout(最終評価用)

docs/IMPROVEMENT_PROPOSALS.md の案 01。仕事・日常のチャット・技術・固有名詞(地名・人名)・数字・ニュース調を
20 問ずつ(`domain`)、うち 7 問に前の文(`context_text`)。重み・候補の数・閾値などを選ぶのには使わない
(使ったら、その旨をここに書き、新しい最終評価用のセットを作る)。`eval_baseline.py` は分野ごとの Acc@1 も出す。

許容する表記の基準(結果を見る前に決めた。結果を見てから都合よく足さない):

- 数字: 半角・全角、自然な場合は漢数字(「3時」「３時」「三時」)。桁区切りのカンマ。
- 送り仮名の一般的な揺れ(「打ち合わせ / 打合せ」「締め切り / 締切」「売り上げ / 売上」「税込み / 税込」)。
- 漢字とかなの揺れは、どちらも一般的なものだけ(「良かった / よかった」「方 / ほう」「ご飯 / ごはん」)。
- 単位の記号(「メートル」→「ｍ」)、歴史的な表記(「大坂城」)は誤りとする。

結果(2026-09-30、RTX 3060、前の文あり、docs/adr/0024 の後):

| | 全体 | 仕事 | チャット | 技術 | 固有名詞 | 数字 | ニュース |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Mozc 単体 | 84.2% | - | - | - | - | - | - |
| Low(zenz-medium) | 98.3% | - | - | - | - | - | - |
| Standard | 97.5% | 20/20 | 20/20 | 20/20 | 19/20 | 18/20 | 20/20 |
| High | 97.5% | - | - | - | - | - | - |

Mozc が正しく、Standard・High が誤った問題: 「五十音順」→「５０音順」。どの品質も「200メートル」→「２００ｍ」
(単位の記号)、Standard・High は「大阪城」→「大坂城」。

## 指標

予測(`mozc/eval_predict.py`、決まった言い回し 29 問): 当たり、節約できた文字数(当たった候補のうち打った部分の
変換より長い分)、外れ候補の割合(予測の候補のうち正解の文の先頭にならないもの)。2026-09-30 の Standard、
1 秒待ってから Tab: 当たり 16/29、節約 4.0 文字 / 問、外れ候補 76.4%。
同梱の LLM(TinySwallow-1.5B)の量子化を、f16 から同じ手順で作って比べた(2026-10-01、Standard、調整用 5 セットの
正解数の合計 / Tab の当たり): Q4_K_M 356 / 10、**Q5_K_M 360 / 16(今のまま)**、Q6_K 359 / 13。Q4_K_M は約 140 MB 小さいが
変換も予測も落ち、Q6_K は良くならない。手元で作った Q5_K_M はインストール先のものとハッシュが一致した(作り方の再現)。

試して採らなかったこと: AI の候補を、1 位との 1 トークンあたりの log P の差(0.5 / 1.0 / 1.5)で出さないようにしても、
外れ候補は 75.4〜76.7% でほぼ変わらず、当たりは最大 16 → 14 に落ちた(確からしさの差では当たりと外れを見分けられない)。

Low(zenz-medium、LLM なし)の生成した文の減点(`KOTORI_LM_GEN_PENALTY`)を調整用のセットで比べた(2026-09-30):
0.5(今の値)が最もよい。1.0 ではニュアンス 85 → 80%、2.0 では AJIMEE 88.0 → 85.5%・ニュアンス 75%。
Mozc が正しく Low が誤った問題は 0.5 で AJIMEE 2、日常・慣用句・ニュアンス 各 1、漢数字 0。


- Acc@1、Acc@10: 正解(許容する表記のいずれか)が第 1 候補、上位 10 件に入った割合
- CER: 第 1 候補と最も近い正解との文字単位の編集距離の和を、その正解の文字数の和で割った値
