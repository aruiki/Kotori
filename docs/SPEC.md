## 1. 概要と目標

本プロジェクト(仮称 **Kotori IME**)は、ネットワーク接続なしで動作するニューラル言語モデル搭載の日本語かな漢字変換IMEを、OSSとして開発する。位置づけは開発者本人が私用で使うベータ版(v0.9-beta)で、到達目標は「Google日本語入力より優秀な変換精度と、ATOKに近い使用感」である。判定は測定可能な受け入れ基準(14.3)で行う。

### 1.1 製品目標

- **変換精度**:文脈を考慮した一括変換で、Google日本語入力の実測値を上回る第1候補正解率
- **使用感**:打鍵ごとの反応が知覚できない速さ(p99 30ms以内、13章)、誤入力補正、予測入力、自然な学習
- **完全ローカル**:入力内容・学習データを端末外へ一切送信しない。テレメトリもない
- **OSS**:ソースコードはGitHubで公開する。ただしベータ版では一般配布を想定せず、署名・インストーラ整備・公開パッケージ化は行わない

### 1.2 前提(ユーザー未確定のため本書で仮置き)

| 項目 | 仮置きの決定 | 理由 |
| --- | --- | --- |
| 利用者 | 開発者本人1名 | 私用ベータ。一般配布・サポートはしない |
| 対象OS | Windows 11(x64)。ARM64はビルドのみ維持 | 利用者の常用環境と仮定(19.2で確認) |
| エンジン実装言語 | Rust(stable、MSRV 1.80) | メモリ安全、C ABIを出しやすい、将来の他OS対応が容易 |
| 推論ランタイム | llama.cpp(ggml)をFFI経由で利用 | CPU最適化と量子化が成熟 |
| 言語モデル | 公開済みのzenz-v2.5系を利用 | 自前学習はベータ後(18.7) |
| 署名・配布 | コード署名なし。GitHubからのソースビルドまたは未署名バイナリ+インストールスクリプト | 私用のため費用と手間を省く |
| コードのライセンス | Apache-2.0 OR MIT のデュアル | 既存資産と両立する |

本書で「v1.0」と書かれた要件は、ベータ版(v0.9)の要件と読み替える。前提が変わる場合は、2章・10章・16章を優先して改訂する。

ベータ版で省く機能は2.3に、ベータ後の拡張は18.7にまとめる。

### 1.3 本書の読み方(実装エージェント向け)

- 「**MUST**」は必須要件、「**SHOULD**」は強い推奨、「**MAY**」は任意を表す(RFC 2119準拠)
- 各要件には `REQ-<章>-<番号>` のIDを付け、コミット・PR・テストはこのIDを参照する
- 実装順序は18章のマイルストーンに従う。章番号順ではない
- 本書に記載のない判断が必要な場合は、19章「未決事項」に追記してから、最も保守的な選択で先に進める

## 2. スコープと非目標

ベータ版はWindows 11でのローマ字入力による日本語入力に集中し、他OS、公開配布、クラウド連携は含めない。

### 2.1 対象OSと優先順位

| 優先 | OS | フロントエンド技術 | 時期 |
| --- | --- | --- | --- |
| P0 | Windows 11(x64) | TSF(Text Services Framework)、C++ + Rust | ベータ(M3) |
| P1 | macOS 13以降 | InputMethodKit、Swift | ベータ後 |
| P1 | Linux(fcitx5) | fcitx5アドオン、C++ | ベータ後 |
| 対象外 | iOS、Android | — | 予定なし |

エンジンはOS非依存に作り、CIではLinuxでもビルド・テストする。これによりベータ後の他OS対応を安くする。

### 2.2 ベータ版のスコープ(MUST)

- ローマ字入力、ライブ変換(既定は無効)、明示変換(スペースキー)
- 文節区切りの伸縮・移動・個別再変換
- ニューラルLMによる文脈考慮変換(確定済み左文脈を利用)
- 予測入力、誤入力補正、ユーザー学習、ユーザー辞書
- 全角/半角・カタカナ・英数・日付時刻などの特殊変換
- MS-IME互換のキー配列(ATOK・Google互換プリセットはSHOULD)
- 最小限の設定GUIとユーザー辞書編集、Google日本語入力/MS-IME形式からの辞書インポート

### 2.3 非目標(ベータ版では扱わない)

- コード署名、公証、MSIインストーラ、winget等での公開配布
- macOS、Linux、モバイル対応
- JISかな入力(SHOULD 扱い。時間があれば実装)
- クラウドLLM・外部APIへの接続、手書き・音声入力、校正支援
- 自前モデルの学習(ベースラインのzenzで目標を満たせない場合のみ前倒し)
- 多人数での試用評価、サポート体制
- GPU必須の機能。GPUは使わず、CPUのみで全要件を満たす

## 4. システムアーキテクチャ

変換処理はすべてユーザーごとに1つ動く独立プロセス `kotori-server` に集約し、OSフロントエンドはキー受付と描画だけを担う薄い層とする。これによりエンジンのクラッシュやモデル推論の遅延がアプリ本体を巻き込まず、3OSでエンジンを共通化できる。

&#91;embedded content: システム構成 · 4プロセス、エンジン内6モジュール、データ3種\]

キー入力は上から下へ流れ、候補は右上の候補ウィンドウへ返る。フロントエンドは推論を一切行わない。

### 4.1 プロセス構成

| プロセス | 実行場所 | 責務 | 実装 |
| --- | --- | --- | --- |
| OSフロントエンド | 各アプリのプロセス内(Windows)/ IME専用プロセス(macOS)/ fcitx5プロセス内(Linux) | キーイベント受付、プリエディット描画、左文脈・周辺テキスト取得、確定文字列の挿入 | 10章参照 |
| `kotori-server` | ユーザーごとに1プロセス、常駐 | 変換・予測・学習・辞書・設定の全処理 | Rust |
| `kotori-renderer` | ユーザーごとに1プロセス(Windowsのみ) | 候補ウィンドウ、予測ポップアップ、モード表示の描画 | Rust + Direct2D/DirectWrite |
| `kotori-config` | 必要時のみ起動 | 設定GUI、ユーザー辞書ツール、学習データ管理 | Rust + Tauri 2 |

- **REQ-4-1** `kotori-server` はフロントエンドから初回接続時に起動し、ユーザーごとに単一インスタンスであること(Windows:名前付きミューテックス、Unix:ロックファイル)。MUST
- **REQ-4-2** フロントエンドは `kotori-server` の異常終了を検知したら、指数バックオフ(100ms起点、最大5s)で再起動する。再接続までは直接入力モードで動作し、アプリの入力を妨げないこと。MUST
- **REQ-4-3** macOSでは候補ウィンドウをIMEプロセス内のパネルで、Linux(fcitx5)ではfcitx5標準の候補UIで描画する。`kotori-renderer` はWindows専用とする。SHOULD

### 4.2 IPCプロトコル

- **トランスポート**:Windowsは名前付きパイプ `\\.\pipe\kotori-<ユーザーSID>` とし、ACLで当該ユーザーのみに接続を許可する。macOS/Linuxは `$XDG_RUNTIME_DIR/kotori/server.sock`(macOSは `~/Library/Application Support/Kotori/`)のUNIXドメインソケット、パーミッション0600とする。MUST

## 5. 変換エンジン仕様

変換は「辞書ラティスでN-best候補を作り、ニューラルLMで並べ替える」ハイブリッド方式とする。辞書ラティスが固有名詞と読みの網羅性を、LMが文脈判断を担い、LMが使えない状況(モデル未導入、低スペック機)でもラティス単体で実用精度を出す。

### 5.1 処理パイプライン

1. **Composer**:キー列 → 読み(カタカナ正規形)+ 各かなに対応する生キー列
2. **Lattice Builder**:読みの各開始位置から辞書を共通接頭辞検索し、ノードを配置
3. **Viterbi + A\***:最小コスト経路と、上位N件(既定 N=50)の文全体候補を得る
4. **Reranker**:上位K件(既定 K=16)をニューラルLMで再スコアリング(6章)
5. **Segmenter**:第1候補を文節に区切り、各文節の代替候補リストを作る
6. **Learner 補正**:ユーザー学習による順位補正(8章)
7. **Output**:プリエディット、候補ウィンドウ内容を組み立てて返す

### 5.2 ローマ字かな変換(Composer)

- **REQ-5-1** 変換規則はTSV(`入力 \t 出力 \t 保留`)で定義し、実行時に差し替え可能とする。既定表はMS-IME互換とし、ATOK互換表、AZIK表を同梱する。MUST
- **REQ-5-2** 「nn」「n'」「子音重ね→っ」「xtu/ltu」「wi/we」、全角記号(「-」→「ー」、「\[」→「「」)を既定表で扱う。MUST
- **REQ-5-3** 各かなに、それを生んだ生キー列を保持する。F10(半角英数)変換、誤入力補正(9章)、「ローマ字のまま確定」に使う。MUST
- **REQ-5-4** JISかな入力を別の規則表で提供し、濁点・半濁点の後置結合を扱う。MUST
- 読みの内部表現はカタカナ(NFC正規化済み)とし、表示時にひらがなへ変換する。「ヴ」「ー」はそのまま保持する。

### 5.3 辞書

#### システム辞書の形式

| 項目 | 仕様 |
| --- | --- |
| 1エントリの内容 | 読み、表記、左文脈ID、右文脈ID、生起コスト(i16)、属性フラグ(固有名詞、環境依存文字、旧字体、人名など) |
| 索引 | 読みをキーとするダブル配列トライ。共通接頭辞検索と予測(前方一致)検索の両方に対応 |
| 連接コスト | 左右文脈ID(品詞ID)の行列、i16。Mozcの品詞体系(id.def)を採用し互換を保つ |
| バイナリ形式 | リトルエンディアン、ヘッダにマジック `KTRD`、形式バージョン、SHA-256、セクションオフセット |
| 読み込み | mmapで読み取り専用に開く。起動時にチェックサム検証し、不一致なら起動を拒否してエラーを記録 |
| サイズ目標 | ディスク60MB以下、常駐メモリ(RSSの私有部分)10MB以下 |

- **REQ-5-5** 辞書はビルド時にTSVソースから `kotori-dictc` ツールで生成する。ソースと生成物の対応は再現可能(同一入力から同一バイナリ)であること。MUST

#### 辞書ソース(ライセンス詳細は16章)

| 区分 | ソース | 用途 |
| --- | --- | --- |
| 基本語彙・品詞・連接コスト | Mozc の dictionary\_oss | ベース辞書 |
| 補助語彙 | SudachiDict(core) | 新語・複合語の補完。品詞はMozc体系へ写像 |
| 固有名詞 | Wikipedia日本語版の記事名 | 別パッケージ「固有名詞辞書」として分離し、ライセンスを分ける |
| 絵文字・記号 | Unicode CLDR の日本語アノテーション | 「はーと」→ ♡ ❤️ など |
| 郵便番号・住所 | 日本郵便の郵便番号データ | 任意導入の追加辞書 |

#### 特殊変換(動的に生成する候補)

- 数字:半角・全角・漢数字・大字・位取り(「12345」→「1万2345」「一万二千三百四十五」「12,345」)
- 日付・時刻:「きょう」「あした」「いま」→ 当日の日付・時刻を複数書式で(和暦を含む)
- 文字種:ひらがな、全角カタカナ、半角カタカナ、全角英数、半角英数(生キー列から)
- 単位・記号:「へいほうめーとる」→ ㎡ m² など

### 5.4 ラティス構築と探索

- **REQ-5-6** 読み長 n に対し、各開始位置 i で辞書を共通接頭辞検索し、終了位置ごとにノードを置く。辞書にない部分を埋める未知語ノード(ひらがな/カタカナそのまま、1〜8文字)を高コストで常に追加し、経路が必ず存在することを保証する。MUST
- **REQ-5-7** 文字の追加・削除時は、変更位置より前のノードを再利用する差分構築とする。1文字追加時の再構築コストは末尾近傍のみに比例すること。MUST
- 前向きViterbiで各ノードの最小累積コストを求め、後ろ向きA\*探索でN-bestを列挙する。表記が同一の経路は重複除去する。
- 経路コストは次式で計算する。

```latex
\mathrm{cost}(w_1 \dots w_m) = \sum_{k=1}^{m} \Bigl( \mathrm{word}(w_k) + \mathrm{conn}(\mathrm{rid}(w_{k-1}), \mathrm{lid}(w_k)) + \mathrm{user}(w_k) \Bigr)
```

`user(w)` はユーザー学習による補正値(負値で優遇)で、8章で定義する。

### 5.5 文節区切りと文節候補

- 文節は「自立語1つ + 後続の付属語(助詞・助動詞・接尾辞)」とし、品詞ルール表で判定する(Mozcのセグメンタ規則を参考に独自に定義)。
- **REQ-5-8** 文節にフォーカスがあるとき、その区間の読みに対する候補を「文全体N-bestでその区間に出た表記」→「区間単独のラティス上位」→「文字種変換」の順に並べ、重複を除く。候補数は最大200件。MUST
- **REQ-5-9** 文節区切りをユーザーが変更したら、変更した境界を固定制約としてラティスを再探索し、他の文節も再計算する。MUST

### 5.6 候補の注釈

- **REQ-5-10** 環境依存文字、旧字体、人名、絵文字、日付などの種別を候補ウィンドウの注釈として表示する。MUST
- 同音異義語の意味注釈(ATOKの「同音語用例」相当)は、注釈データを別パッケージとし SHOULD とする。データソースは19章の未決事項とする。

## 6. ニューラル言語モデル仕様

かな漢字変換に特化した小型のデコーダ型Transformerを、CPUで1打鍵あたり20ms以内に動かし、辞書ラティスの候補を文脈で並べ替える。モデルは3サイズを用意し、端末性能に応じて自動選択する。

### 6.1 モデル構造

| 項目 | 仕様 |
| --- | --- |
| 構造 | デコーダのみのTransformer(Llama系:RMSNorm、RoPE、SwiGLU)。llama.cppで推論できる構造に限定する |
| トークン化 | 文字単位。語彙は日本語常用文字+JIS第1〜第4水準+記号+特殊トークンで約8,000 |
| 入力形式 | `<ctx>` 左文脈 `<in>` 読み(カタカナ)`<out>` 変換結果 `</s>` |
| 最大系列長 | 256トークン(左文脈は最大96文字に切り詰め) |
| 任意入力 | `<prof>` ユーザープロフィール文(例:「物理学者」)を先頭に付けられる。既定は空 |

| サイズ | パラメータ数 | 量子化 | 想定環境 | ファイルサイズ目安 |
| --- | --- | --- | --- | --- |
| `xs` | 約30M | Q8\_0 | 省電力ノート、ARM64 Windows | 35MB |
| `s`(既定) | 約90M | Q8\_0 | 一般的なノートPC(4コア以上) | 100MB |
| `m` | 約300M | Q4\_K\_M / Q8\_0 | GPU搭載機、デスクトップ | 200〜320MB |

初期開発ではzenz-v2.5系(xsmall 26M、small 91M、medium 310M)をベースラインとして使い、同等以上の精度を自前モデルで達成した時点で置き換える。

### 6.2 推論方式

LMは次の2モードで使う。既定はモードAのみで、モードBは精度向上オプションとする。

**モードA:リランク(MUST)**

- 左文脈と読みまでのプレフィックスを1回だけ計算してKVキャッシュに保持し、K件の候補を共有プレフィックスのバッチとして一度に採点する。
- 打鍵で読みが1文字伸びた場合は、左文脈部分のKVキャッシュを再利用する。
- 候補 c の最終スコアは次式とし、重みは開発用データで最適化してモデルファイルのメタデータに格納する。

```latex
S(c) = \log P_{\mathrm{LM}}(c \mid \mathrm{ctx}, \mathrm{reading}) - \lambda_1 \cdot \frac{\mathrm{cost}_{\mathrm{lattice}}(c)}{T} + \lambda_2 \cdot \mathrm{bonus}_{\mathrm{user}}(c)
```

**モードB:制約付き生成(SHOULD)**

- N-best に正解がない場合に備え、LMが読みに整合する表記を自ら生成する。生成中の各時点で「出力済み表記が、読みのある接頭辞をラティス上で説明できる」ことを確認し、整合しないトークンをマスクする。
- ラティス第1候補を下書きとして一度に検証する投機的デコーディングで高速化する(Zenzaiで実用化済みの手法)。
- 生成結果は候補リストの第1〜第3位のいずれかに差し込む。第1位にするのは、LMスコアがモードAの最良候補を閾値以上上回った場合のみとする。

### 6.3 レイテンシ予算と劣化動作

- **REQ-6-1** 基準機(13章)で、モデル `s` のリランク(K=16、読み20文字、左文脈64文字)が p95 で20ms以内に完了すること。MUST
- **REQ-6-2** 締め切り(既定25ms)を過ぎた推論結果は、そのキー応答には使わず、完了次第プリエディットを差分更新する。ただし、ユーザーがすでに候補ウィンドウを開いている場合は、表示中の順位を変えない。MUST
- **REQ-6-3** 起動時の簡易ベンチマークで、基準を満たす最大サイズのモデルを自動選択する。ユーザーは設定で上書きできる。MUST
- **REQ-6-4** モデルファイルがない、読み込みに失敗した、メモリが不足している場合は、ラティス単体モードで動作を継続し、設定画面に状態を表示する。MUST

### 6.4 実行環境

- 推論ランタイムは llama.cpp を固定バージョン(git submodule でコミットを固定)で静的リンクし、Rust から FFI で呼ぶ。更新は精度・速度の回帰テスト(14章)通過を条件とする。
- CPU推論のみ、既定2スレッド。GPU(Vulkan、Metal)はベータ後のオプションとする。
- モデルはGGUF形式とし、メタデータに `kotori.model_version`、`kotori.vocab_hash`、`kotori.score_weights`、`kotori.license` を必須で含める。`vocab_hash` がエンジン側と一致しない場合は読み込みを拒否する。
- **REQ-6-5** モデルはサーバー起動後にバックグラウンドで読み込み、読み込み完了前の変換はラティス単体で処理する。起動からキー受付までを遅らせないこと。MUST

## 8. ユーザー学習・ユーザー辞書

ユーザー学習は確定履歴をローカルのSQLiteに記録し、ラティスのコストとLMスコアの両方に補正を掛ける方式とする。v1.0 ではモデル重みの追加学習(ファインチューニング)は行わない。

### 8.1 学習する情報

| 種別 | 記録内容 | 使い道 |
| --- | --- | --- |
| 語の選択 | 読み、表記、品詞ID、選択回数、最終選択日時 | 同じ読みで選んだ表記を上位に出す |
| 連接 | 直前の確定語、読み、表記、回数 | 「前の語がXのときはY」の文脈的な選好 |
| 文節区切り | 読み、ユーザーが指定した区切り位置 | 同じ読みで次回から同じ区切りにする |
| 予測の採用 | 入力途中の読み、採用した予測候補、回数 | 予測候補の順位 |
| 未知語 | 辞書にない読みと表記の組(ユーザーが文字単位で組み立てて確定したもの) | 自動で語として追加(学習辞書) |

### 8.2 補正の計算

- 語の補正値は次式とし、半減期 H は既定30日とする。直前に選んだ表記は、回数によらず次回の第1候補とする(ATOK・MS-IMEと同じ挙動)。

```latex
\mathrm{bonus}_{\mathrm{user}}(w) = a \cdot \log(1 + \mathrm{count}(w)) \cdot 2^{-\Delta t / H} + b \cdot \mathbb{1}[w \text{ が直前の選択}]
```

- **REQ-8-1** 学習による順位変更は、同じ読みに対する候補の順位だけを変え、読みの異なる変換結果の精度を下げないこと。回帰テスト(14章)で検証する。MUST
- **REQ-8-2** 候補ウィンドウで候補を選んで Ctrl+Delete を押すと、その候補の学習情報を削除する。MUST

### 8.3 学習しない状況

- **REQ-8-3** 次の場合は学習もログ記録も一切行わない。MUST
  - パスワード入力欄、または InputScope 等でパスワード・暗証番号と申告された入力欄
  - ユーザーが「シークレットモード」(学習停止)を有効にしている間
  - 設定で除外したアプリ(既定でパスワードマネージャーを列挙)
- 数字のみ、8文字以上の英数字混在列、メールアドレス形式の確定文字列は、誤ってパスワードやIDを覚えないよう学習対象から除外する。

### 8.4 保存と容量

- 保存先はユーザーデータディレクトリの `learning.sqlite3`(12章)。WALモードで開き、学習書き込みスレッドが最大5秒ごとにまとめて書き込む。
- 上限は既定10万件。超えた場合は補正値の低いものから削除する。
- 学習データのエクスポート/インポート/全消去を設定画面から行える。

### 8.5 ユーザー辞書

- 項目:読み(ひらがな)、表記、品詞(名詞、人名、地名、組織名、短縮よみ、顔文字、動詞などの簡易分類から選択)、コメント。内部ではMozc品詞IDに写像する。
- 複数の辞書ファイルを持てて、辞書ごとに有効/無効を切り替えられる。
- **REQ-8-4** 次の形式のインポートに対応する:Microsoft IMEのテキスト形式(UTF-16LE)、ATOKのテキスト形式、Google日本語入力/Mozcのエクスポート形式、本IMEのTSV形式。文字コードを自動判定し、取り込めなかった行は理由付きで一覧表示する。MUST
- ユーザー辞書の語は、同じ読みのシステム辞書語よりも既定で優先する。
- 「短縮よみ」品詞は、読み全体が一致した場合にのみ候補として出す(例:「めあど」→ 自分のメールアドレス)。

## 9. 予測入力・誤入力補正・再変換

ATOKの使用感を決める補助機能として、予測入力、誤入力補正、再変換、確定アンドゥを v1.0 に含める。いずれも「間違った介入をしない」ことを精度より優先する。

### 9.1 予測入力(サジェスト)

- **REQ-9-1** 読みが2文字以上(設定で1〜4)になった時点で、プリエディット下に最大5件の予測候補を表示する。Tab または ↓ で予測候補に移り、Enter で確定する。MUST
- 候補の出所と優先順位:
  1. ユーザー履歴の前方一致(最近・高頻度のもの)
  2. ユーザー辞書・システム辞書の前方一致(生起コスト順)
  3. LMによる続きの生成(読みに整合する表記の後に、最大8文字の続きを生成)。モデル `s` 以上で有効。SHOULD
- 予測候補の計算はキー応答とは非同期に行い、締め切り(40ms)に間に合わない場合は前回の予測表示を消して次の打鍵を待つ。
- 確定直後の「次の語句の予測」(読み未入力での予測)は MAY とし、既定で無効にする。

### 9.2 誤入力補正

| 誤りの種類 | 例 | 生成方法 |
| --- | --- | --- |
| 隣接キーの打ち間違い | konnnitiha → konnnichiha 系の誤打 | キー配列(QWERTY/JIS)の隣接表による置換 |
| 文字の入れ替わり | ikutsu → ikusu 系 | 隣り合う2キーの交換 |
| 抜け・重複 | shinbu / shinnbunn | 1キーの挿入・削除 |
| 読みの誤り | おうきい / おおきい、ずつ / づつ | かな単位の揺れ規則表 |

- 生キー列(REQ-5-3)に対して、重み付き編集で補正読みを生成する。編集回数は1回まで(読み8文字以上は2回まで)、補正読みは最大8件とする。
- 補正読みから得た候補には補正ペナルティを加算する。
- **REQ-9-2** 補正候補が第1候補になるのは、元の読みに妥当な経路がない(ラティス最小コストが閾値超え)かつLMスコアが閾値以上の差で上回る場合に限る。それ以外は第2〜3候補に置き、候補ウィンドウに「補正」の注釈を付ける。MUST
- **REQ-9-3** 誤補正率(正しく入力したのに補正候補が第1候補になる割合)を0.3%以下に保つ。14章の誤入力テストセットで測定する。MUST

### 9.3 再変換

- **REQ-9-4** 確定済み文字列を選択して変換キーを押すと再変換する。フロントエンドは選択文字列と前後文脈をOSの再変換APIで取得する(Windows:TSFの再変換、macOS:IMKの選択範囲取得)。MUST
- エンジンは表記から読みを推定する逆変換を行う。システム辞書に表記→読みの逆引き索引を持たせ、ラティスで最小コストの読みを選ぶ。
- 読みの推定を誤りうるため、再変換時の候補ウィンドウに読みの修正手段(Shift+→/← で文節長調整、読みの直接編集)を用意する。

### 9.4 確定アンドゥ

- **REQ-9-5** 確定直後(次のキー入力前)に Ctrl+Backspace を押すと、確定した文字列を削除して確定前の変換状態に戻す。対応しないアプリ(周辺テキストの削除APIがない)では何もしない。MUST

## 10. OSフロントエンド仕様

フロントエンドはOSのIME APIへの薄いアダプタとし、変換ロジックを持たない。全OS共通のIPCクライアントは Rust の `kotori-client` クレート(C ABIで公開)として実装し、各フロントエンドから呼ぶ。工数とリスクが最も大きいのはWindowsで、全体工数の3割程度を見込む。

### 10.1 Windows(TSF)

**構成**

- TSFのText Input Processor(TIP)をインプロセスCOM DLL `kotori_tip.dll` としてC++20で実装する(COM実装の実績と安定性を優先。Mozcの実装を設計の参考にする)。
- **REQ-10-1** x64 PCでは64bitアプリ用(x64)と32bitアプリ用(x86)の両方のDLLを登録する。片方が欠けると一部アプリで入力できなくなる。ARM64 PC用(ARM64、ARM64EC)はCIでビルドのみ維持する。MUST

**実装するTSFインターフェース**

| インターフェース | 目的 |
| --- | --- |
| `ITfTextInputProcessorEx` | TIPの起動・終了 |
| `ITfKeyEventSink` | キー入力の受付(`OnTestKeyDown` で消費判定を先に行う) |
| `ITfCompositionSink` / 編集セッション | プリエディットの作成・更新・確定 |
| `ITfDisplayAttributeProvider` | 入力中・変換中・注目文節の下線と色 |
| `ITfThreadMgrEventSink` / `ITfThreadFocusSink` | フォーカス移動時のセッション切替 |
| `ITfCompartment` 監視 | IMEオン/オフ、入力モードの同期 |
| `ITfFnReconversion` | 再変換(9.3) |
| `ITfUIElement` / `ITfCandidateListUIElement` | UIレスモード(全画面ゲームが自前で候補を描く場合) |
| `ITfLangBarItemButton` | タスクバーの入力モード表示 |

**要件**

- **REQ-10-2** 左文脈はカーソル位置から最大256文字をTSFの範囲APIで取得する。取得できないアプリでは左文脈なしで変換する。MUST
- **REQ-10-3** InputScopeがパスワード・暗証番号の入力欄では、IMEを直接入力にし、学習を停止する(REQ-8-3)。MUST
- **REQ-10-4** ストアアプリ(AppContainer)や低整合性レベルのプロセスからもエンジンに接続できるよう、名前付きパイプのセキュリティ記述子に「すべてのアプリケーションパッケージ」と低整合性ラベルを付与する。ただし接続元が同一ユーザーであることは必ず検証する。MUST
- **REQ-10-5** 管理者権限で動くアプリ、ログオン画面・UACの安全なデスクトップでは、学習と辞書書き込みを行わない。安全なデスクトップではIMEを無効とする。MUST
- **REQ-10-6** 同期編集セッションが拒否された場合は非同期で再試行し、キー入力の順序を保つ。キー入力を取りこぼさないこと。MUST
- **REQ-10-7** 候補ウィンドウは `kotori-renderer` で描画し、DPI(Per-Monitor V2)、マルチモニタ、ダークモード、ハイコントラストに対応する。候補位置はTSFの文字位置APIで取得したキャレット矩形に合わせる。MUST

**配布**

- ベータ版はMSIを作らず、PowerShellの `install.ps1` / `uninstall.ps1` でファイル配置とTIPの登録・解除(`regsvr32`)を行う。管理者権限で実行する。
- コード署名は行わない。未署名DLLでもTSFへの登録と読み込みは可能だが、SmartScreenやウイルス対策ソフトの警告が出る場合の対処をREADMEに書く。

### 10.2 macOS(InputMethodKit)

- Swiftで `IMKInputController` のサブクラスを実装し、`~/Library/Input Methods/Kotori.app` として配置する。エンジンは同じアプリバンドル内のヘルパー実行ファイルとして起動する。
- 入力中表示はマーク付きテキスト、候補ウィンドウは自前の `NSPanel` で描画する(`IMKCandidates` は機能不足のため使わない)。
- 左文脈は `attributedSubstring(from:)` で取得する。
- **REQ-10-8** セキュア入力(パスワード欄)が有効な間は学習を停止する。MUST
- **REQ-10-9** 公開配布する場合はDeveloper IDで署名し公証を通す(ベータ後)。SHOULD
- GPU推論はMetalを使う(6.4)。

### 10.3 Linux(fcitx5)

- C++でfcitx5アドオン `fcitx5-kotori` を実装し、候補表示はfcitx5の入力パネルを使う。
- 左文脈はfcitx5の周辺テキスト機能(SurroundingText)で取得し、対応しないアプリでは文脈なしで変換する。
- パッケージ:deb(Ubuntu LTS)、rpm(Fedora)、AUR、Flatpak拡張。
- IBus版はv1.x以降(2章)。

### 10.4 互換性テスト対象アプリ

ベータ版はWindows行のうち利用者が普段使うアプリを優先して確認する(19.2)。他OSの行はベータ後に使う。

| OS | 対象アプリ |
| --- | --- |
| Windows | メモ帳、Word、Excel、Outlook、Edge、Chrome、Firefox、Windows Terminal、VS Code、Slack、Teams、LINE、エクスプローラーの名前変更、UWP版電卓、全画面ゲーム(UIレス)、管理者権限のコマンドプロンプト |
| macOS | テキストエディット、Pages、Safari、Chrome、Terminal、VS Code、Slack、Word |
| Linux | GTK4/Qt6アプリ、Firefox、Chrome、VS Code、Alacritty、LibreOffice |

## 11. UI/UXとキー操作仕様

### 11.1 状態遷移

## 12. 設定・データ保存形式

設定は人が読めるTOML、学習データとユーザー辞書はSQLiteに保存し、すべてユーザーごとのディレクトリに置く。書き込みは一時ファイル+リネームで原子的に行い、電源断でも破損させない。

### 12.1 保存場所

| OS | 設定 | データ(学習・辞書・ログ) | 同梱の辞書・モデル |
| --- | --- | --- | --- |
| Windows | `%APPDATA%\Kotori\` | `%LOCALAPPDATA%\Kotori\` | `%ProgramFiles%\Kotori\data\` |
| macOS | `~/Library/Application Support/Kotori/` | 同左 | アプリバンドル内 `Contents/Resources/` |
| Linux | `$XDG_CONFIG_HOME/kotori/` | `$XDG_DATA_HOME/kotori/` | `/usr/share/kotori/` |

| ファイル | 内容 |
| --- | --- |
| `config.toml` | 全設定 |
| `learning.sqlite3` | 学習履歴(8章) |
| `userdict.sqlite3` | ユーザー辞書(複数辞書を1ファイル内で管理) |
| `models/` | 追加でダウンロードしたモデル(`m` サイズなど) |
| `logs/` | 動作ログ。入力内容は記録しない(15章) |

### 12.2 config.toml(既定値)

```toml
schema_version = 1

[general]
keymap = "ms-ime"          # ms-ime | atok | google
romaji_table = "ms-ime"    # ms-ime | atok | azik | カスタムファイルパス
input_method = "romaji"    # romaji | kana
live_conversion = false

[conversion]
nbest = 50
rerank_k = 16
use_left_context = true
typo_correction = true

[prediction]
enabled = true
min_chars = 2
max_items = 5
lm_continuation = true

[learning]
enabled = true
half_life_days = 30
max_entries = 100000
excluded_apps = []

[model]
size = "auto"              # auto | xs | s | m | off
threads = 2
gpu = "auto"               # auto | off
profile = ""               # ユーザープロフィール文(6.1)

[ui]
theme = "system"           # system | light | dark
font_size = 14
candidates_per_page = 9
show_mode_indicator = true
punctuation = "、。"
```

- **REQ-12-1** 設定ファイルには `schema_version` を持たせ、エンジンは起動時に旧版から自動移行する。移行前のファイルは `config.toml.bak.<版>` として残す。MUST
- **REQ-12-2** 不正な値は既定値で置き換えて起動を継続し、置き換えた項目を設定GUIに警告表示する。設定の誤りでIMEが使えなくなってはならない。MUST
- **REQ-12-3** 設定変更はIPC `SetConfig` で即時反映し、再起動を要求しない(モデルサイズ変更を除く)。MUST

### 12.3 モデルと辞書の同梱方針

- 辞書一式とモデル `xs`、`s` をビルド時に取得・生成し、`install.ps1` が配置する。
- `m` モデルは利用者が手動でダウンロードし、`models/` に置けば設定で選べる。
- **REQ-12-4** `kotori-server` はネットワークに一切アクセスしない。モデルと辞書の取得はビルドスクリプトだけが行い、SHA-256を検証する。MUST

## 13. 非機能要件:性能・リソース・安定性

打鍵から表示更新までを p99 30ms 以内に収めることが最重要の非機能要件で、これを満たせない機能は既定で無効にする。数値はすべて基準機で測定し、CIのベンチマークで継続監視する。

### 13.1 基準機

| 区分 | 構成 | 用途 |
| --- | --- | --- |
| 利用者のPC | 未確定(19.2) | ベータ版の性能判定の正式な基準 |
| CI上の参考値 | GitHub Actions の windows-latest | 性能劣化の検知(絶対値の判定には使わない) |
| 仮の基準 | Intel Core i5-1135G7 相当(4コア8スレッド)、メモリ8GB | 利用者PCが決まるまでの設計目標 |

### 13.2 性能・資源の目標値

| 指標 | 目標値 | 測定条件 |
| --- | --- | --- |
| キー応答(辞書ベース第1候補の表示) | p50 5ms、p99 15ms | 読み20文字、ライブ変換有効 |
| キー応答(リランク反映まで) | p95 20ms、p99 30ms | モデル `s`、K=16、左文脈64文字 |
| 変換キー押下から候補表示 | p99 30ms | 読み40文字 |
| 予測候補の表示 | p95 40ms | モデル `s` |
| エンジン起動からキー受付可能 | 300ms 以内 | モデルはバックグラウンド読込 |
| モデル読み込み完了 | 1.5秒以内 | モデル `s`、SSD |
| 常駐メモリ(エンジン) | 250MB 以下(`s`)、120MB 以下(`xs`)、40MB 以下(モデルなし) | 1時間の連続使用後 |
| アイドル時CPU使用率 | 0.1% 以下 | 入力なし5分間の平均 |
| フロントエンドDLLのメモリ増分 | 1アプリあたり5MB 以下 | Windows |

### 13.3 安定性

- **REQ-13-1** 24時間の連続ランダム打鍵試験(ファジング的な入力生成)で、エンジンのクラッシュ、デッドロック、メモリリーク(RSS増加10%超)がないこと。MUST
- **REQ-13-2** フロントエンドがホストアプリをクラッシュ・フリーズさせないこと。フロントエンド内のすべてのCOMメソッドは例外を外に漏らさず、IPC呼び出しには必ずタイムアウトを設ける。MUST
- **REQ-13-3** 学習データ・設定ファイルが破損している場合は、退避(`.corrupt.<日時>`)してから新規作成し、起動を継続する。MUST
- クラッシュ時はミニダンプ(Windows)/クラッシュログをローカルに保存する。送信はしない。ユーザーが手動でIssueに添付できるよう、設定GUIに「診断情報を書き出す」機能を設ける(入力内容は含めない)。

## 14. 評価と品質保証、受け入れ基準

「Google日本語入力より優秀」は、同一の評価セットでGoogle日本語入力を実測し、その差で判定する。公開ベンチマーク(AJIMEE-Bench)と自前テストセット(KTB)の両方で第1候補正解率がGoogle日本語入力を上回ることを、ベータ版の受け入れ条件とする。ATOKは比較できれば参考値として測る。

### 14.1 評価セット

| 名称 | 規模 | 内容 | 主な指標 |
| --- | --- | --- | --- |
| [AJIMEE-Bench](https://github.com/azooKey/AJIMEE-Bench) | 200問(初版) | 誤変換が実際に起きた文。左文脈付きの問題を含む | Acc@1、CER |
| KTB-conv(自作) | 5,000文 | ニュース、ビジネスメール、チャット、技術文書、小説の5分野×1,000。左文脈付き | Acc@1、Acc@10、CER |
| KTB-typo(自作) | 1,000件 | 実際の打ち間違いを収集・合成した入力と正解 | 補正成功率、誤補正率 |
| KTB-predict(自作) | 2,000件 | 入力途中の読みと、続けて入力された語句 | 上位5件の的中率、節約打鍵率 |
| KTB-reconv(自作) | 500件 | 確定済み文字列と正しい読み | 読み推定の正解率 |
| 回帰ゴールデン | 2,000件以上 | 過去に修正した誤変換と必ず正解すべき基本例 | 全件一致 |

- KTBは7.2の test 分割から作り、分野ごとに人手で正解を確認する。作成手順と正解確認の基準を `eval/README.md` に記録する。
- **REQ-14-1** 評価はすべて `kotori-eval` コマンド1つで実行でき、結果をJSONとMarkdownの表で出力する。MUST

### 14.2 商用IMEとの比較方法

- Windows上で、テスト用アプリに `SendInput` で読みを打鍵し、変換・確定した結果を読み取る計測ツール `kotori-imebench` を作る。Google日本語入力(Mozc)、Microsoft IME、本IMEを同じ手順で計測する。ATOKは利用者が所有している場合のみ計測する。
- 左文脈は、テスト用アプリの入力欄に事前に確定済みの文を置くことで与える。
- Google日本語入力のエンジンはOSSのMozcとほぼ同系統のため、Mozcをライブラリとして直接呼ぶ高速な比較経路もSHOULDとして用意する(CIで毎回比較できる)。

参考として、公開情報では AJIMEE-Bench における Google日本語入力の Acc@1 は54.0%とされている([さくらのナレッジ](https://knowledge.sakura.ad.jp/42901/))。一方、33.5Mパラメータの公開モデルが Acc@1 80.5%、CER 2.55%を報告している([kanakanji-edge-33m](https://huggingface.co/yuuki14202028/kanakanji-edge-33m))。ニューラル方式では80%台が現実的な水準である。

### 14.3 ベータ版の受け入れ基準

| 項目 | 基準 |
| --- | --- |
| AJIMEE-Bench Acc@1(モデル `s`) | Google日本語入力の実測値 +10ポイント以上(目安 75%以上) |
| KTB-conv Acc@1(モデル `s`) | Google日本語入力の実測値を上回る(5分野すべてで) |
| KTB-conv Acc@1(ラティス単体) | Google日本語入力の実測値から3ポイント以内 |
| KTB-typo | 補正成功率60%以上、誤補正率0.3%以下 |
| KTB-predict | 上位5件の的中率がGoogle日本語入力以上 |
| 性能・資源 | 13.2 の全項目を利用者のPCで満たす |
| 互換性 | 利用者が普段使うアプリで重大な不具合(入力不能、文字化け、クラッシュ)なし |
| 実利用 | 利用者本人が2週間、普段のIMEをKotoriに切り替えて使い続けられる |

### 14.4 テストの種類とCIゲート

| 種類 | 内容 | 実行タイミング | 失敗時 |
| --- | --- | --- | --- |
| 単体テスト | 各クレートのテスト。Composer・ラティスは性質ベーステスト(proptest)を含む | 全PR | マージ不可 |
| 回帰ゴールデン | 14.1 のゴールデン全件 | 全PR | マージ不可 |
| 精度評価 | AJIMEE-Bench と KTB-conv の縮小版(1,000文) | 全PR | Acc@1 が0.3ポイント以上低下でマージ不可 |
| 性能ベンチ | criterion によるラティス・推論の計測、13.2 の簡易版 | 全PR | 10%以上の劣化でマージ不可 |
| IPC結合テスト | サーバーを起動しキー列を流して出力を検証 | 全PR | マージ不可 |
| フロントエンドE2E | Windows:UI Automation でテスト用アプリに入力。macOS:XCUITest | mainへのマージ後、毎晩 | Issueを自動作成 |

## 15. セキュリティ・プライバシー

IMEはすべてのキー入力を見るため、最も機密性の高いソフトウェアの一つとして扱う。入力内容は端末外に出さず、ディスクにも学習に必要な最小限しか残さない。

### 15.1 プライバシー要件

- **REQ-15-1** `kotori-server`、`kotori-renderer`、フロントエンドはネットワーク通信を行うコードを含まない。依存クレートも含めてネットワーク系ライブラリのリンクをCIで検査する(`cargo deny` と依存グラフ検査)。MUST
- **REQ-15-2** ログに入力文字列、読み、候補、左文脈を記録しない。ログに出す文字列は長さとハッシュ(ソルト付き)のみとする。デバッグビルドでも既定で同じとし、明示的な環境変数でのみ解除できる。MUST
- **REQ-15-3** 左文脈はメモリ上でのみ扱い、学習データへは「直前の確定語1語」以外保存しない。MUST
- テレメトリ、クラッシュレポートの自動送信は実装しない(2.3)。
- 学習データ・ユーザー辞書のファイルはOSのユーザー権限(Windows:ユーザーのみのACL、Unix:0600)で作成する。

### 15.2 攻撃面と対策

| 脅威 | 対策 |
| --- | --- |
| 他ユーザー・他プロセスによるIPC乗っ取り | パイプ/ソケットをユーザー単位に分離しACLで制限。接続元のユーザーSID/UIDを検証(REQ-10-4) |
| 細工したIPCメッセージによるメモリ破壊 | Rust で実装し、メッセージサイズ上限(1MB)と全フィールドの範囲検証。IPCパーサをcargo-fuzzで継続ファジング |
| 細工した辞書・モデルファイル | ヘッダとチェックサム検証。GGUFの読み込みはサイズ・形状を検証してから llama.cpp に渡す。取得物はSHA-256で検証(REQ-12-4) |
| ユーザー辞書インポートの不正ファイル | 行単位でパースし、1行1KB・総数100万行の上限。失敗行は無視して報告 |
| 管理者権限アプリ・安全なデスクトップ経由の情報漏えい | 学習停止・IME無効化(REQ-10-5) |
| サプライチェーン | 依存の固定(Cargo.lock、submoduleのコミット固定)、`cargo audit` をCIで実行、リリースビルドの再現性確保、GitHub Actions の最小権限化 |

### 15.3 脆弱性対応

- `SECURITY.md` に報告窓口(GitHub の Private vulnerability reporting)を記載する。
- 重大な脆弱性は報告から14日以内の修正リリースを目標とする。

### 17.2 コーディング規約

- Rust:edition 2021、`rustfmt`、`clippy -D warnings`。`unsafe` は `kotori-lm` と `kotori-client` のFFI境界に限定し、各ブロックに `// SAFETY:` コメントを書く。
- エラー処理:ライブラリは `thiserror`、バイナリは `anyhow`。キー処理経路で `unwrap` / `expect` を使わない。
- C++:C++20、`clang-format`、MSVCは `/W4 /WX`。COMメソッドは例外を外に出さない(REQ-13-2)。
- Swift:SwiftLint を使う。
- Python(学習):`ruff`、型ヒント必須、依存は `uv.lock` で固定。
- 大きな生成物(辞書バイナリ、モデル、データセット)はリポジトリにコミットしない。取得スクリプトとSHA-256を置き、CIでキャッシュする。

### 17.3 ブランチ・PR・CI

- `main` は保護ブランチ。変更はすべてPR経由とし、CIの全ゲート(14.4)通過を必須とする。
- コミットメッセージは Conventional Commits 形式とし、関係するREQ IDを本文に書く(例:`feat(lattice): 差分構築を実装 (REQ-5-7)`)。
- CIマトリクス:ubuntu-latest(エンジン)、windows-latest(x64、エンジンとフロントエンド)。ARM64ビルドの確認は週1回の定期実行とする。

### 17.4 AIエージェント向け作業規約(AGENTS.md に記載する内容)

1. 作業開始前に `docs/SPEC.md` の該当章と `docs/adr/` を読む。
2. 18章のマイルストーン順に進め、現在のマイルストーンの完了条件にない機能には着手しない。
3. 1つのPRは1つの目的に絞り、差分は原則600行以下にする。テストのない機能追加はしない。
4. PRを出す前に `just ci`(フォーマット、lint、テスト、ゴールデン、縮小評価、ベンチ)をローカルで通す。
5. 仕様にない判断が必要なら、`docs/adr/NNNN-<題>.md` に選択肢と理由を書き、最も保守的な案で進める。仕様との矛盾を見つけたら、実装を止めてIssueを立てる。
6. `docs/SPEC.md` の変更は、人間のメンテナの承認があるPRでのみ行う。
7. ネットワークにアクセスする依存を `kotori-server` 系に追加しない(REQ-15-1)。
8. 精度または性能の数値が下がる変更は、PR本文に評価結果の前後比較を貼る(REQ-14-2)。
9. Windows固有のコードはLinux上では検証できないため、windowsランナーのCI結果で確認してからマージする。

## 19. リスクと未決事項

最大のリスクはWindows TSFの互換性問題と、打鍵ごとの推論レイテンシである。どちらも早期(M2、M3)に実機で検証し、ダメな場合の逃げ道を先に決めておく。

### 19.1 リスク

| リスク | 影響 | 対策・代替案 |
| --- | --- | --- |
| 特定アプリでTSFが正しく動かない | その場で入力できない | 利用者が普段使うアプリから順に検証。問題アプリは除外リストで直接入力に切替 |
| リランクが20msに収まらない | 打鍵が重く感じる | `xs` モデルへ自動降格、Kを8へ削減、2段階応答で体感を守る |
| ベースラインモデルの精度が想定以下 | Google日本語入力を超えられない | `m` モデル併用、自前学習(18.7)を前倒し |
| 署名なしバイナリをWindowsが警告・隔離する | インストールできない | ローカルビルドを推奨手順とし、SmartScreen の解除手順をREADMEに記載 |
| 読み付与誤りによる学習データの質低下 | 精度の頭打ち | 読み検証ステップ(7.2-6)の除外率を監視 |
| llama.cpp の破壊的変更 | ビルド不能 | submodule のコミット固定と回帰テスト通過後のみ更新 |
