# Kotori日本語入力 改善案

作成日: 2026-09-30

対象: [aruiki/KotoriIME-japanese- の main](https://github.com/aruiki/KotoriIME-japanese-/tree/3b0181218aa745bbfeb4aa6c6dd3997346603b9f)
（確認時のコミット: `3b0181218aa745bbfeb4aa6c6dd3997346603b9f`、PR #92）。

本書は、公開リポジトリと同じコミットのコード・評価記録・ADR を読んでまとめた**改善の提案**です。
実装、仕様変更、Issue・PR の作成は含みません。新しいベンチマークや Windows 実機試験も実施していません。
コードから考えられる改善余地と、記録済みの問題を区別しています。

## 1. 現状の捉え方

現在の製品は **Mozc を土台に、zenz の生成と TinySwallow の採点を加えた Windows IME**です。
改善は、この土台を維持して「普段の入力でも正確」「操作を待たせない」「安心して更新できる」を固める方向がよいと考えます。
旧 Rust エンジンや自前 TSF の未完了項目は、現 Mozc 版の未実装機能とは分けて扱います。[根拠: ADR 0012][adr12]

記録上の現在地は次のとおりです。数値は今回の再測定ではありません。

| 項目 | 現在の記録 | 読み取る際の条件 |
| --- | --- | --- |
| AJIMEE-Bench Acc@1 | Low 86.5%、Standard 91.5%、High 92.5% | 200 問、前の文あり。候補数の選択にも使用したセット |
| 日常文 Acc@1 | Standard / High 97.5% | 81 問。LLM の重み選択にも使用したセット |
| 変換の速さ | Standard 中央値 約 65〜70 ms | RTX 3060 の測定。CPU のみの端末への保証値ではない |
| Tab の速さ | 1 秒待ってからなら中央値 43 ms、すぐ押すと 536 ms | 予測キャッシュが間に合うかで差がある |
| AI 予測の的中 | 上位 3 件 58.6% | 決まった言い回し 29 問。日常全体を代表するとは限らない |

出典: [評価記録][eval]、[ADR 0016][adr16]、[ADR 0020][adr20]、[ADR 0021][adr21]、[ADR 0023][adr23]。

AI 予測の非同期化、Tab でのキャッシュ再利用、生成中のキャンセル、長文の処理上限、
設定画面の刷新、GPU / VRAM の表示、予測の切替、モデル同梱 MSI、MSI の版更新は実装済みです。
以下は、これらを踏まえた追加の改善案です。[根拠: Mozc の説明][mozc]、[ADR 0019〜0022][adr19]、[版更新の作業カード][msi-card]

## 3. 改善案の詳細

### 01. 調整用と最終評価用のデータを分ける

- **現状**: 生成数を AJIMEE で選び、日常 81 問は LLM の重み選択にも使っています。これらは有用な回帰セットですが、未知の文章への性能は別に確認したい状態です。[根拠][adr16]、[根拠][adr23]
- **案**: 現行セットを調整・回帰用として残し、未使用の評価用セットを追加する。まず日常、仕事、技術、固有名詞、数字・記号を分けた数百文から始め、確認手順を整えて段階的に増やす。
- **効果**: 小さな既知セットでの改善と、日常全体への改善を分けて判断できます。
- **確認方法**: 重み・候補数を固定してから評価用セットを開く。出典・類似文単位の重複を除き、分野別 Acc@1、CER、問題数、信頼区間、Mozc 正解 → Kotori 誤りの件数を残す。前の文あり・なしも分ける。
- **留意点**: 許容表記は出力を見て都合よく追加せず、人手確認の基準を先に決める。既存モデルの学習データとの完全な非重複は、確認可能な範囲を明記する。

### 02. Mozc の精度・回帰テストを CI に接続する

- **現状**: 通常 CI は Rust 版のテストが中心で、Mozc 側のワークフローは MSI のビルドが中心です。4 セットを比較する道具はありますが、品質判定への接続を補う余地があります。[根拠: 通常 CI][ci]、[Mozc CI][mozc-ci]、[評価ツール][eval-all]
- **案**: 読みの検証、生成の足切り、文全体の第 1 候補の保護、設定変更、キャッシュ、キャンセルをモデルなしでも確認できるテストにする。PR では小さな回帰セット、リリース候補ではモデル込みの全評価を行う。
- **効果**: 「東京特許許可局」の修正や、入力中に AI 処理を待たせない修正を継続して守れます。
- **確認方法**: 判定を意図的に壊した場合に CI が失敗することを確認する。評価データや取得・変換スクリプトの変更も対象にし、Windows 固有の変更は Windows で検証する。
- **留意点**: 評価器も、プロセス異常終了・出力不足・タイムアウトを失敗として返す必要がある。現在の `eval_baseline.py` は終了コードを確認せず、`eval_all.sh` の `tail` も失敗を見えにくくするため、接続前にここを固める。[評価器][evaluator]

### 03. Space・Tab の待ち時間を制御する

- **現状**: 入力中の AI 予測は非同期ですが、予測が未完成の Tab はその場で計算します。記録では即 Tab の中央値 536 ms、最大 990 ms です。[根拠][adr21]
- **案**: Space とキャッシュ不在の Tab に時間予算を設ける。時間内に完成しない場合は Mozc の候補で操作を続けられるようにし、実測に応じて AI の処理量を選ぶ。AI 結果の差分更新が必要かは別案として検討する。
- **効果**: 起動直後、GPU が遅い端末、長い入力でも、変換操作が長く止まる場面を減らせます。
- **確認方法**: 初回・通常時・即 Tab・長文・予測直後の Space を分け、候補の初回表示と最終 AI 結果の時間を別々に測る。背景処理の割り込みから推論資源が空くまでの時間も測る。
- **留意点**: 生成のトークン単位キャンセルは既存です。追加案は採点のバッチ境界などへの拡張です。表示中・選択中の候補順位は固定し、時間予算や差分更新方式は ADR と承認対象の仕様整理を経て決める。[現実装][lm-control]

### 04. 予測キャッシュの設定・セッション境界を明確にする

- **現状**: キャッシュは読み・文脈で再利用し、ジョブは設定を保持します。キャッシュ項目には品質・モデル・設定世代がありません。設定変更後に古い結果が表示された実機事例は、今回確認していません。[根拠][cache]
- **案**: 品質、モデル識別子、設定世代を再利用条件に含め、古い世代のジョブ結果を採用しない。入力先の変更、セッション終了、シークレットモード、AI 予測 OFF 時のジョブ取消・キャッシュ処理も定義する。
- **効果**: 設定した状態と実際の予測が一致し、文脈を別の入力先へ持ち越さない保証を作れます。
- **確認方法**: 同じ読みのまま品質・モデルを変更し、変更前のジョブを遅延させる。合成の秘密文字列を使い、シークレット切替や入力先変更後の候補・ログ・保存ファイルを検査する。
- **留意点**: 上流 Mozc による呼び出し制御も調べた上で不足部分だけ補う。漏えいがあると断定する案ではありません。ネットワークに触れない方針と既定の入力ログ抑制は維持する。

### 05. 実アプリ・更新・長時間の受け入れ試験を揃える

- **現状**: 現在の負荷試験は `converter_main` にコマンドを送る短い試験です。MSI の版更新は修正済みですが、作業カードには実機での上書き確認が残っています。[負荷試験][stress]、[版更新カード][msi-card]
- **案**: インストール済み Mozc 版を、メモ帳、ブラウザ、Office、VS Code、Terminal、x86 アプリ、管理者アプリで試す。IME 切替、確定、文節操作、フォーカス移動、パスワード欄、複数画面も含める。
- **効果**: 変換器単体では分からない入力不能、候補表示の問題、更新で古いファイルが残る問題を配布前に拾えます。
- **確認方法**: 旧 MSI → 新 MSI、入力アプリを開いたままの更新、削除 → 再導入、旧版への復帰を試す。設定・辞書・学習、実行ファイルの版とハッシュを比較する。リリース候補では 24 時間の継続試験でメモリ・VRAM・ハングを監視する。
- **留意点**: 自動化が難しい操作は結果付きの確認表にする。旧版へ直接上書きできるとは仮定せず、検証した復帰手順を案内する。旧 Rust TIP の試験と現 Mozc 製品の試験を分ける。

### 06. AI の生成文を部分修正しやすくする

- **現状**: zenz が生成した文は全体を 1 文節として扱います。ほぼ正しい文でも、一語だけ直す操作のしやすさには改善余地があります。[根拠][adr16]、[生成文の区切り][segmentation]
- **案**: 読みと表記の対応を使って、安全に区切れる生成文には文節情報を付ける。対応が曖昧な場合は現行の全文 1 文節を維持する。
- **効果**: 同音異義語や固有名詞が一か所だけ違うとき、全文を戻して打ち直す負担を減らせます。
- **確認方法**: 左右移動、Shift＋左右、候補変更、部分確定、取消を実 IME で試し、修正までの打鍵数を比較する。文全体の正解率と文字列も維持する。
- **留意点**: 単なる文字数分割は行わない。文全体で選んだ結果を後の文節処理が上書きしない、ADR 0020 の対策も守る。

### 07. Mozc の正答とユーザーの意図を守る

- **現状**: LLM が短い文で zenz の正しい判断を覆す問題は、重み 0.7 への変更で改善されています。一方、読みの一致だけで意味や表記の好みまで正しいとは言えません。[根拠][adr23]
- **案**: Mozc が正解だった問題の退行を独立して追う。短文、固有名詞、ユーザー辞書、数字・単位を重点に、点差が小さい場合の Mozc 優先や、明示的な候補選択・文節変更を AI が覆さない保護を小さく比較する。
- **効果**: AI が自然さを優先しすぎて、名前や利用者が選んだ表記を変える場面を減らせます。
- **確認方法**: ユーザー辞書に登録した語、敬語、数字、表記揺れのセットで、保護の有無による正解率・退行数・修正打鍵数を比較する。
- **留意点**: 既存の先頭候補保護と重複させない。新しい閾値は独立した開発用データで選び、固有名詞全体を一律に AI の対象外にするような広い制限は避ける。

### 08. 実際に動いている AI の状態を表示する

- **現状**: 設定画面の GPU 情報は DXGI の機器情報です。実際の推論可否は llama.cpp の GPU 検出とモデル読み込みにも依存します。[GPU 表示][gpu-ui]、[モデル準備処理][model-state]
- **案**: 設定画面に「準備中」「zenz のみ」「LLM 使用中」「モデルを読み込めない」を表示し、実際のモデル・実行環境・再試行方法を詳細欄に置く。
- **効果**: AI を有効にしたのに効いていない場合、原因と対処が分かります。
- **確認方法**: GPU なし、Vulkan 利用不可、モデル・DLL の欠損、モデルパス変更で表示と実動作を照合する。入力文字列を含まない診断情報を確認する。
- **留意点**: すでにある GPU 名・VRAM 表示を増設し直す案ではありません。利用者に必要な状態を短く示し、開発者向けの内部情報は詳細欄へ置く。

### 09. 機種別・操作別の性能表を作る

- **現状**: 主な製品の速度・資源記録は RTX 3060 の測定です。Low の速度も、GPU なしの全端末を代表する値としては扱えません。[根拠][readme]、[資源計測][adr19]
- **案**: CPU のみ、内蔵 GPU、低 VRAM の GPU、NVIDIA / AMD の代表機で、品質別の速度・メモリ・VRAM を比較する。品質のおすすめは VRAM 容量だけでなく実際の利用可否と速度で裏付ける。
- **効果**: 「GPU はあるが重い」端末も含め、自分に合う品質を選びやすくなります。
- **確認方法**: 起動直後と読み込み後を分け、通常入力・Space・即 Tab・長文で p50 / p95 / p99 と最大値を記録する。1 時間使用後と待機時の資源も測る。
- **留意点**: 共有メモリを使う内蔵 GPU は専用 VRAM だけで判断しない。任意の短い端末測定を導入するなら、測定中の負担とおすすめ変更の理由も説明する。

### 10. 予測を「節約打鍵数」と「邪魔になりにくさ」で評価する

- **現状**: 現行の 29 問は決まった言い回しが中心です。ADR には古い表記や無関係な続きの課題も記録されています。[根拠][adr18]
- **案**: 未使用のメール・チャット・仕事文で、的中率に加え、節約打鍵数、候補選択の手数、不適切な続きを提示した割合、表示までの時間を測る。
- **効果**: 当たりが出ることだけでなく、入力の邪魔をせず役に立つかを判断できます。
- **確認方法**: 複数の妥当な語尾・敬語・表記を人手で定義し、一定の打鍵間隔で比較する。誤った数字、断定、敬語を含む候補も確認する。
- **留意点**: 現在の予測スイッチは入力中と Tab の両方に効きます。まず説明を合わせ、需要があれば「自動表示は控え、Tab では使う」選択を検討する。[設定の決定][adr22]

### 11. 配布物と評価結果の再現情報を残す

- **現状**: Mozc・モデルの取得元固定、同梱 DLL の SHA-256 固定、MSI の SHA-256 添付はあります。一方、評価結果の JSON に実行条件はなく、`eval_all.sh` は品質を変えると同じ出力先を上書きします。[評価器][evaluator]、[評価ツール][eval-all]、[配布 CI][mozc-ci]
- **案**: Low / Standard / High の結果を別々に保存し、ソース・Mozc・パッチ・モデルのハッシュ、推論 DLL の版、品質、CPU / GPU、ドライバー、データ版を小さな manifest にまとめる。取得検証は量子化用 CPU ZIP など未確認の経路にも広げる。
- **効果**: 「どの版・どの構成で出た数字か」が分かり、不調や精度差を再現しやすくなります。
- **確認方法**: 同じ manifest で再実行し、問別結果とモデル構成を照合する。生成 GGUF はハッシュのほか、読み込みと既知候補の採点を短く試す。
- **留意点**: 量子化の直接変換で点数が異常になった記録があるため、ファイルが存在するだけを成功条件にしない。同梱 DLL の既存ハッシュ検証と、MSI の既存 SHA-256 添付を未実装扱いしない。[量子化の記録][adr16]、[LLM 変換手順][llm-build]

### 12. 現行の文書・導入案内・比較条件を揃える

- **現状**: README は現 Mozc 版ですが、HANDOFF の進捗や次の作業、ライセンス表などには旧版の記述が残っています。ダウンロード・clone の URL にも旧名 `aruiki/Kotori` が残っています。[引き継ぎ][handoff]、[作業一覧][tasks]、[ライセンス表][licenses]、[導入案内][readme]
- **案**: 現行 Mozc 版の状態と旧 Rust 版の履歴を区別し、入口・取得 URL・同梱物・確認待ちを揃える。導入、初回起動、品質選択、更新、復帰を一続きの案内にする。成功例は人手で意味も確認し、既知の失敗例・制限を添える。
- **効果**: 次の開発者が旧 renderer の課題へ戻ったり、利用者が端末条件を誤解したりすることを減らせます。
- **確認方法**: リンク、MSI の内容、設定画面、評価記録を突き合わせる。Google 日本語入力・Microsoft IME との比較は、同じ Windows アプリ、文脈、学習状態、版、手順で始める。まず少数の手動比較でもよい。
- **留意点**: Mozc 単体 51.0% を製品版 Google 日本語入力の成績として扱わない。比較未実施の説明を維持する。SPEC の構成・GPU 方針・性能条件の改訂は別の承認付き PR で扱い、ベータ版と Latest の公開方針も文書化する。

### 13. Mozc パッチを目的ごとに追いやすくする

- **現状**: パッチ 0002 に変換、生成、予測、推論ランタイム、設定画面などがまとまっています。パッチの再生成と適用確認の道具はすでにあります。[構成][mozc]、[再生成ツール][patch-tool]
- **案**: 上流への変更と追加ファイルを追いやすい形にし、目的別の差分・テスト・担当する ADR が分かる索引を用意する。必要なら目的ごとのパッチ分割を検討する。
- **効果**: Mozc や llama.cpp の更新時に、どの変更を守る必要があるか判断しやすくなります。
- **確認方法**: 固定 Mozc の素のツリーへ順に適用し、再生成後の差分、ビルド、回帰結果が一致するか確認する。
- **留意点**: 並べ替えや大量の機械的整形だけの PR は避ける。既存ツールを生かし、今後の変更を 1 目的の小さな PR に保ちやすくする。

### 14. 設定画面のアクセシビリティを確認する

- **現状**: Fluent 風の設定画面には明るい固定色のスタイルが使われています。外観の刷新は済んでおり、今回表示障害を再現したわけではありません。[根拠][gpu-ui]
- **案**: OS のハイコントラスト、文字拡大、キーボード操作、読み上げに合わせ、必要な箇所だけ補う。品質名には利用者向けの意味も併記する。
- **効果**: 拡大表示や読み上げを使う人も設定を変更でき、品質の選択で迷いにくくなります。
- **確認方法**: 100 / 150 / 200% DPI、文字拡大、ダーク・ハイコントラスト、Tab キーのみの操作、Windows Narrator で確認する。
- **留意点**: 設定画面や Mozc の候補 UI を全面的に作り直す提案ではありません。

### 15. 生成と採点の間の再計算を減らす

- **現状**: バッチ内の共有接頭辞と、512 トークン単位の投入は実装済みです。一方、採点する組の間や生成と採点の間では KV を消して計算し直す箇所があります。[根拠][scoring]
- **案**: 計測で効果が見込める場合に、同一要求の生成 → 採点、複数バッチ間、LLM の同じ前文の計算を再利用する。
- **効果**: モデルを大きくせず、精度を保って Space・Tab を速くできる可能性があります。
- **確認方法**: 生成、zenz 採点、LLM 採点を別々に測り、候補ごとの対数確率と最終選択が現行と一致するか確認する。VRAM / RAM の増分と破棄条件も測る。
- **留意点**: 速くなるとは事前に断定しない。モデル・文脈・設定が異なる場合は再利用せず、共有接頭辞の既存実装を重複して追加しない。

## 4. 着手順の提案

1. **案 12 の文書整理と、案 11 の評価結果保存から始める。** 小さな変更で、以後の判断の前提を揃えられる。
2. **案 01・02 で独立した評価と回帰確認を作る。** これを、変換精度や処理方式を変える前の基準にする。
3. **案 03〜05・09 で入力の待ち時間、設定変更、実アプリ、更新を確認する。** 体感の問題を測定可能にする。
4. **案 06〜08・10 を、一番困る利用場面から個別に検討する。** 新しい評価で効果が確認できた案を採用する。
5. **案 13〜15 は、運用負担や計測結果に応じて進める。** パッチ整理や高速化そのものを目的にしない。

大きなモデルへの置換、自前 TSF の再実装、クラウド推論、他 OS への拡張を先に進めるより、
現行 Windows 版の品質を確かめる基盤を優先する案です。
採用した案は現行の段階と承認済み仕様に照らし、1 目的の作業カード・PR に分けることを想定しています。
