# 0033. 生成の前置きを打鍵をまたいで使い回し、根どうしで共有する

- 状態: 採用
- 日付: 2026-10-01
- 関係: docs/adr/0024(負荷を下げる)、0032(1 回の計算のまとまり)、作業カード 36

## 背景

入力中の AI の計算(Standard、RTX 3060、`cost_bench.py`)は稼働率 47.1% で、その 78% が LLM(TinySwallow)による
予測の続きの生成だった。打鍵ごとの軽い予測は、読み全体の変換と、最後の 1 文字を打ちかけとみなした変換の 2 つを根に
して、1 回のビームサーチでまとめて続きを作る(`BeamSearch` の複数の根)。

根が複数のときは、毎回すべての根の前置き(前の文 + 変換)を初めから計算し直していた。前置きの使い回し(`UsePrefix`)は
根が 1 つのときだけだった。また、前置きの計算と、最初の分布を得る最後のトークンの計算を別々に呼んでいた。

## 決めたこと

`BeamSearch` の前置きの計算を、根の数によらず次のようにする。

1. 根 0 の前置き(最後の 1 トークンより前)はシーケンス 0 に置き、前回の呼び出しと同じ所は計算し直さない
   (打鍵ごとに、前の文と変換の大半は変わらない)。終わったら根 0 の前置きを残す(`KeepPrefix`)。
2. ほかの根は、根 0 と同じ先頭(前回から残っている所まで)をシーケンス 0 から写し(`llama_memory_seq_cp`)、
   残りだけを計算する。
3. 前置きの残りと、すべての根の最後のトークンを、なるべく 1 回の計算にまとめる(GPU では呼ぶ回数が効く)。
   やめる関数があるときは、これまでと同じく 32 トークンずつ計算して、その間にやめられるようにする。

候補と点数は変わらない(同じ前置きの KV を使うだけ)。

## 結果(RTX 3060)

入力中の AI の計算(`cost_bench.py`、日常の文 12、170 打鍵):

| | 稼働率 | zenz の計算 | LLM の計算 | zenz のトークン | LLM の呼び出し |
| --- | ---: | ---: | ---: | ---: | ---: |
| 前 | 47.1〜47.5% | 4966 ms | 17191 ms | 10754 | 1200 |
| 後 | **42.6%** | 3817 ms | 16179 ms | **6838** | **1045** |

予測(`eval_predict.py`、29 問。1 回ごとに 1〜2 問揺れる):

| | 入力中の候補(0.3 秒後) | 入力中の候補(0.05 秒後) | Tab(1 秒後) |
| --- | ---: | ---: | ---: |
| 前 | 16 | 10 | 16 |
| 後 | 16 | 14 | 16 |

変換の精度(`eval_all.sh`)は変わらない: Low 88.0%、Standard 91.5%、High 92.5%(AJIMEE)、日常 97.5%。
負荷試験(`stress_test.py`)は GPU・CPU とも異常終了なし(Tab の最大 859 ms、CPU の変換の最大 568 ms)。
GPU のない PC の Space(`space_latency.py KOTORI_LM_DEVICE=cpu`)は中央値 296 ms、最大 480 ms、正解 15/15。

## 採らなかった案

- 打鍵ごとの軽い予測を 100 ms 待ってから始める(`KOTORI_LM_LIGHT_DELAY=100`): 稼働率は 31.9% まで下がるが、
  打ってすぐ(0.05 秒後)の当たりが 14 → 5 に減る。入力中の候補は次の打鍵のときにしか出し直されないので、
  予測は次の打鍵までに出来ている必要がある。
- 軽い予測の並べ替えを省く(`KOTORI_LM_LIGHT_RANK=0`)、続きの数を減らす(`KOTORI_LM_LIGHT_BEAMS=1,2,6`):
  稼働率は 41〜42% になるが、0.3 秒後の当たりが 16 → 13〜14 に減る。
- 続きのトークンを 4 にする(`KOTORI_LM_LIGHT_BEAMS=2,3,4`): 稼働率 43.6%、当たりは同じだが当たった候補が短くなる
  (11.2 → 10.6 文字)。前置きの共有の方が、同じ以上に減って当たりも変わらない。
