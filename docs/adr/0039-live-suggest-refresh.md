# 0039. 手が止まったら、入力中の候補を AI の変換と予測で取り直す

- 状態: 採用
- 日付: 2026-10-02
- 関係: docs/adr/0018〜0021(入力中の予測)、0024(先回りの変換)、0025(予測のキャッシュ)、0029(待ちの解消)、作業カード 48

## 背景

メンテナの指摘(2026-10-02): 「スペースを押す前のリアルタイムの段階で、正しい変換を表示できないか。今は Mozc の変換が出て、
スペースを押してから正しい変換に変わる。Tab の候補予測も同様」。

入力中の候補の窓は、**キーを押したときにしか作り直されない**。AI の変換は Space のとき、AI の予測は裏で計算して次の打鍵で
出すので、打ち終わって手を止めると、窓には Mozc の変換(「彼は公園で公園をした」)が残る。裏で作った Tab と同じ品質の
予測も、次のキーを押すまで出ない(docs/HANDOFF.md の「試して効かなかったこと」に記録あり)。

Space の AI の選び方は、Mozc の変換が作る文全体の候補(`kotori_sentences`、変換の要求でだけ作られる)を使うので、
裏のスレッドだけでは Space と同じ答えを出せない。

## 選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. 打鍵ごとに AI の変換をする | 入力中の候補の要求の中で変換する | 打鍵ごとに 50〜100 ms 待たせる(目標は 30 ms 以下)。不採用 |
| B. 裏で選んで次の打鍵で出す | 今の予測と同じ | 手を止めたときに出ない(今の問題そのもの) |
| C. ライブ変換(入力中の文字そのものを変換して見せる) | ATOK・MS-IME のライブ変換 | 操作の感じが大きく変わる(SPEC はライブ変換を既定で無効)。別の判断 |
| **D. 手が止まったら取り直す** | サーバーが出力に「少し後にこのコマンドを送って」(Mozc の `Output.callback`)を付け、TIP がタイマーで送る。サーバーは取り直しで Space と同じ変換をして、候補の先頭に置く | **採用**。打鍵は待たせない。Mozc にもともとある仕組み(callback、TIP の非同期の編集セッション)の上に作れる |

## 決めたこと

1. **サーバー(session)**: 打鍵で入力中の候補を出したら、`Output.callback` に `KOTORI_REFRESH_SUGGESTION` と遅れ
   (GPU あり 200 ms、なし 450 ms)を付ける。取り直しでは入力中の候補を作り直し、**Space と同じ変換**(`kotori_preview`)
   の結果をつないだ文を先頭に置く。予測を使うとき(GPU と LLM)は、800 ms 後にもう一度取り直す(裏で作り直した Tab と
   同じ品質の予測を出す)。1 回の打鍵につき 3 回まで。変換中・確定後の取り直しは何もしない。
2. **変換の AI**: 文全体で選んだ結果を、読み・前の文・設定ごとに覚える(16 件)。取り直しと、その後の Space は覚えた結果を
   使う。**表示した文と Space の結果が必ずそろい**、Space は計算しない。覚えた結果を使うときは、裏の予測の計算を止めない
   (ロックを取らない)。取り直しで止められた裏の予測は、1 回だけやり直す。
3. **TIP**: callback を受けたら、タスクのウィンドウ(既存の非表示のウィンドウ)のタイマーを仕掛ける。キーを押すたびに
   仕掛け直す。鳴ったときにフォーカスが同じ欄なら、非同期の編集セッションでコマンドを送り、返ってきた画面で更新する
   (候補の窓からのクリックと同じ道筋)。サーバーが「使わなかった」と返せば画面を変えない。
4. `KOTORI_LM_LIVE=0` で取り直さない(比べる用)。`KOTORI_LM_LIVE_FIRST`・`KOTORI_LM_LIVE_NEXT` で遅れを変える。

## 結果

セッションの道具(`session_handler_main` に足した `KOTORI_REFRESH`)で、1 文字 0.15 秒おきに打ち、手を止めて
0.2 秒(CPU は 0.45 秒)後と、さらに 0.8 秒後に取り直し、最後に Space(RTX 3060 / CPU、Standard):

| 読み | 打ち終わりの先頭(前) | 取り直し 1 の先頭(後) | 取り直し 1 | 取り直し 2 | Space |
| --- | --- | --- | ---: | ---: | ---: |
| かれはこうえんでこうえんをした | 彼は公園でこうえんをした | 彼は公園で**公演**をした | 67 ms | 3 ms | 2 ms |
| おんせいにんしきのせいどがあがった | 音声認識の精度が上がっただけでなく | 音声認識の**精度が上がった** | 68 ms | 3 ms | 1 ms |
| あしたのかいぎはじゅうじからです | 明日の会議は従事からです | 明日の会議は**１０時**からです | 95 ms | 3 ms | 1 ms |
| (同、GPU なし) | 明日の会議は従事からです | 明日の会議は**１０時**からです | 47 ms | 3 ms | 1 ms |

- 取り直しの先頭と Space の結果: 日常 81 問(前の文なし)で **81 / 81 が同じ**。取り直しの先頭の正解は 79 / 81
  (Space の正解率と同じ 97.5%)。
- 精度(`eval_all.sh`、前の文あり): Standard AJIMEE 91.5%・日常 97.5%、High 92.5%・97.5%(前と同じ)。Low は AJIMEE 87.5%(175 / 200)・日常 97.5%。Low はこの変更の前の main でも
  175 / 200 で、変わらない(記録の 88.0% は前の版のもの。docs/HANDOFF.md に書いた)。
- 単体テスト: `SessionTest.KotoriRefreshSuggestion`(callback の付け方、先頭の置き換え、変換中は何もしない、取り直さない設定)。
- GPU の負荷: 手が止まるたびに 1 回、AI の変換を計算する(GPU で 50〜100 ms)。続けて Space を押せば Space は計算しないので、
  手を止めて Space を押す流れでは計算の量は変わらない。手を止めた後に打ち続けたときだけ増える。

## 注意・残り

- 実機(TSF)での確認が要る。アプリによっては非同期の編集セッションがすぐに許されず、取り直しが遅れることがある。
- 取り直しの先頭は「Space と同じ変換」なので、続きの予測(「お世話になっております」)が 2 番目になることがある。
  Tab の予測(別に作る)は変わらない。
