# 0032: 1 回の計算のまとまりを 256 にして VRAM を減らす

- 状態: 採用
- 日付: 2026-10-01
- 関係: docs/adr/0019(512 に下げた)、0024

## 問題

1 回の計算で扱うトークン数(`kBatch`)は 512 だった(docs/adr/0019 で 4096 から下げた)。結果(ロジット)を受け取る
領域は語彙の大きさ × この数なので、LLM(語彙 15 万)では大きい。一方、Kotori の 1 回の計算は、採点で数十〜200 トークン、
生成で数トークンと小さい。

複数の根をまとめるビームサーチ(docs/adr/0024)は、前置きの合計が `kBatch` を超えると何も生成せずに失敗していた。

## 決定

- `kBatch` を 256 にする。
- 複数の根のビームサーチは、各根の前置きの最後の 1 トークンより前を `kBatch` 以内の組に分けて計算し、最後のトークン
  だけを 1 回でまとめて計算する。前置きがいくら長くても失敗しない。

## 結果(RTX 3060、`perf_table.py`、`cost_bench.py`)

| | VRAM の増分(512 → 256) | メモリ(最大) | 変換 中央値 / p95 |
| --- | --- | --- | --- |
| Low | 532 → 524 MB | 137 → 133 MB | 62 / 83 ms(同じ) |
| Standard | 1656 → **1490 MB** | 488 → 474 MB | 62 / 84 ms(同じ) |
| High | 1655 → **1483 MB** | 565 → 559 MB | 76 / 102 ms(同じ) |

精度(Standard: AJIMEE 91.5%、日常 97.5%)、予測(Tab 16/29)、負荷試験(変換の最大 429 ms)、GPU の稼働率
(46.6% → 46.1%)は変わらない。
