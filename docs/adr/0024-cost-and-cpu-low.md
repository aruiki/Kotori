- 状態: 採用(メンテナの要望: 「RTX 3060 でも入力中に GPU を 30% 近く使う」「精度 90% 以上を保って
  コストを下げる」「ノート PC で 10 文字打って Space を押すと固まる」「ハイエンド向けの仕様は残し、
  精度の高い新しい Low を作る」「設定画面のボタンの文字が消える」)
- 日付: 2026-09-30
- 関係: docs/adr/0016、0018、0019、0021、0022

## 1. 負荷の中身(RTX 3060、Standard)

GPU の使用率はほかのアプリの描画が混ざって揺れるので、AI の計算の時間を数える(`ZenzScorer::Stats`、
`KOTORI_LM_STATS`)。`mozc/tools/cost_bench.py` は日常の文 12 文(170 打鍵)を 1 文字 0.2 秒おきに打ち、
0.8 秒おいて変換する。計算は 1 本のスレッドで順に行うので、計算の時間 / かかった時間 が AI の稼働率に当たる。

- 前: **68.6%**(1 打鍵あたり 191 ms)。大半は入力中の AI 予測の LLM。
- Vulkan では、LLM(1.5B)を 1 回呼ぶ時間が、渡すトークンが 1〜2 なら 5〜6.5 ms、3 以上なら約 14 ms で
  ほぼ一定(`llama-bench`)。計算の量より呼ぶ回数が効く。
- 小さい LLM は精度が足りない(AJIMEE、前の文あり、Standard の中身で LLM だけ替えた): Qwen2.5-0.5B
  87.5%、sarashina2.2-0.5b 87.5%、sarashina2.2-1b 88.0%(TinySwallow-1.5B は 91.5%)。
  1 回の時間もあまり縮まない(呼ぶ回数で決まるため)。TinySwallow のままにする。
- CUDA 版の llama.cpp は Vulkan の 1.5〜2 倍の速さだが、DLL が約 1.1 GB で MSI(上限 2 GB)に入らない。

## 2. 決定(ハイエンド向け。結果を変えない改善)

- 複数の読み・続きを 1 回のビームサーチでまとめて生成する(`ZenzScorer::GenerateMany`・`ContinueMany`)。
  入力中の予測で、読み全体と打ちかけを除いた読みの変換・続きを別々に回していた。
- 止まったとき用の予測の作り直しは、手が 0.6 秒止まってから(`KOTORI_LM_FULL_DELAY`)。続けて打つと
  作り直しは次の打鍵で捨てられていた。
- 採点は、前置きの計算を使い回し(`UsePrefix`)、候補を木にまとめて共通の先頭を 1 回だけ計算する。
- 語彙全体の正規化は、最大値より 20 以上小さい値を足さない(誤差 3e-4 以下)。

| | AI の稼働率 | 入力中の候補(直後 / 0.3 秒後) | Tab(1 秒後) |
| --- | ---: | --- | --- |
| 前 | 68.6% | 7/29 / 15/29 | 17/29 |
| 後 | **49.9%** | 8/29 / 16/29 | 16/29 |

入力中の予測を軽くする案(ビーム 1+1、続きを 4 トークン)は稼働率 36〜38% まで下がるが、Tab の当たりが
12/29 に落ちるので採らない(`KOTORI_LM_LIGHT_BEAMS` で試せる)。

## 3. ノート PC で固まる

原因:

- GPU の判定(`llama_supports_gpu_offload`)が内蔵 GPU でも真になり、1.1 GB の LLM を内蔵 GPU に載せていた。
  内蔵 GPU はメインメモリを共有し、休止からの立ち上がりもあるので、細かく何度も呼ぶ使い方で大幅に遅い。
- 変換(Space)は、裏の予測・モデルの読み込みと同じロックを待ち、AI に使う時間の上限もなかった。

決定:

- AI を載せる GPU は、専用 GPU(`GGML_BACKEND_DEVICE_TYPE_GPU`)で VRAM 3 GiB 以上のもの 1 つだけ
  (`LlamaGpuDevice`)。ほかの GPU にはモデルを分けない。内蔵 GPU だけの PC は CPU で動かす。
- 要求の中ではモデルを読み込まず、裏のスレッドで読む。読み込み中や、ロックが 0.3 秒取れないときは
  AI なしで出す(`TryLockForRequest`)。
- 変換で AI に使う時間の上限: GPU あり 2 秒(保険)、なし 0.6 秒(`KOTORI_LM_BUDGET`)。超えたら生成を
  やめ、Mozc の候補を zenz で採点して選ぶ。
- GPU がなければ、品質の設定に関係なく Low で動かす(LLM は CPU では遅すぎる)。

## 4. 新しい Low(GPU のない PC 向け)

CPU での比較(4 スレッド、LLM なし、前の文あり、時間は AJIMEE の中央値 / p95):

| zenz | ビーム | AJIMEE | 日常 | 時間 |
| --- | ---: | ---: | ---: | --- |
| xsmall | 2 | 71.0% | 92.6% | 52 / 165 ms |
| small | 2 | 85.5% | 93.8% | 188 / 564 ms |
| small | 8 | 85.5% | 93.8% | 299 / 1056 ms |
| medium | 1 | 84.5% | 96.3% | - |
| medium | 2 | **88.0%** | **97.5%** | 805 / 2327 ms |

- Low = zenz-v2.5-medium、ビーム 2、LLM なし。前の Low は xsmall を指していたが、インストール先に
  xsmall がなく small で動いていた(86.5%)。xsmall は 71% なので使わない。medium を MSI に同梱する(333 MB)。
- **先回りの変換**: CPU では 1 回の生成が打鍵の間隔より長い。入力中の候補の要求で、LLM の予測を使わない
  ときは、打つ手が 0.12 秒止まったら今の読みを裏で生成しておく(`RunPreconvert`)。Space では採点だけに
  なる。同じ読みを計算中なら捨てずに待つ。
- Space の応答(CPU のみ、`mozc/tools/space_latency.py`、日常の文 15 文、1 文字 0.15 秒おき):

| 打ち終わってから Space まで | 中央値 | 最大 |
| --- | ---: | ---: |
| 0.15 秒 | 438 ms | 970 ms(上限で打ち切り) |
| 0.35 秒 | 254 ms | 564 ms |
| 0.55 秒 | 130 ms | 336 ms |

## 5. 精度(GPU、前の文あり、Acc@1)

| | AJIMEE | 慣用句 | ニュアンス | 日常 |
| --- | ---: | ---: | ---: | ---: |
| Low(新、medium) | 88.0%(前 86.5%) | 92.0% | 85.0% | 97.5%(前 93.8%) |
| Standard | 91.5%(同じ) | 96.0%(同じ) | 85.0%(同じ) | 97.5%(同じ) |
| High | 92.5%(同じ) | 96.0%(同じ) | 80.0%(前 85.0%) | 97.5%(同じ) |
| Unreal(medium + LLM) | 92.0% | - | - | 96.3% |

High のニュアンスは 1 問(早口言葉)が入れ替わった。ビーム 8 本の生成で、前置きを 2 回に分けて計算する
ようにした数値の差で、生成される候補が変わったため。正規化の近似を外しても同じだった。

## 6. 設定画面のボタンの文字が消える

Windows がダークモードだと、Qt(Fusion)は暗い配色になり、ボタンなどの文字を白にする。設定画面の
スタイルはボタンの背景を白にしていて、文字の色を指定していなかった。アプリの配色を明るいものに固定し
(`GuiUtil::InitQt`)、スタイルで各部品と無効の状態の文字の色を指定する。
