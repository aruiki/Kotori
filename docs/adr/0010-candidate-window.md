# 0010: 候補ウィンドウの描き方と、TIP から renderer への渡し方

- 状態: 採用
- 日付: 2026-09-29

## 背景

仕様では、候補ウィンドウをユーザーごとに1つの `kotori-renderer` プロセス(Rust、Direct2D/DirectWrite)が
描く(4.1、REQ-10-7)。位置は TSF の文字位置 API で取ったキャレットの矩形に合わせる。
PMv2 の DPI、マルチモニタ、ダークモード、ハイコントラストに対応し、画面の端でははみ出さず、
入力中の文字も隠さない(REQ-11-3)。

候補の中身はサーバーの `Output.candidate_window` で TIP に届いている。キャレットの矩形は、
TIP がアプリのプロセスの中で編集セッションを開き、`ITfContextView::GetTextExt` で取るしかない。
候補と位置を renderer へどう渡すかが決まっていない。

## 選択肢

| | (a) TIP → renderer を直接 | (b) サーバー経由 | (c) TIP 内で Win32 のウィンドウ |
| --- | --- | --- | --- |
| 流れ | TIP が Output の候補と、自分で取った矩形を renderer のパイプへ送る | TIP は矩形をサーバーへ送り、サーバーが候補と合わせて renderer へ送る | TIP がアプリのスレッドでウィンドウを作って描く |
| キー1回の IPC | 候補ウィンドウが出ている間、TIP → renderer が1回増える。応答を待たないのでキーの経路は伸びない | 矩形を送るため、TIP → サーバーが1回増える(応答を待つ要求に載せるか、別の要求にする) | 増えない |
| 位置と中身の食い違い | 同じ Output から作るので起きない | 矩形は Output のあとに取るので1キー遅れる。直すには要求を増やす | 起きない |
| AppContainer・低整合性(REQ-10-4) | renderer のパイプにもサーバーと同じ ACL と同一ユーザーの検証が要る | renderer のパイプはサーバーからだけつながればよく、ACL は同じユーザーだけで済む | 要らない |
| UIPI | 表示は問題ない。クリックを TIP に返すとき、管理者のアプリへは PostMessage が届かない(クリックだけ使えない) | クリックはサーバーへ送れるが、TIP へ知らせる経路(サーバーからの通知)がない | 問題ない |
| DPI(REQ-10-7) | TIP が物理座標に直して送り、renderer は PMv2 で描く | 同じ(直す場所が TIP であることは変わらない) | アプリの DPI 設定に引きずられ、DPI 非対応のアプリではにじむ |
| 仕様との関係 | 合う | 合う。サーバーに描画の都合(位置)が入る | REQ-10-7(renderer で描く)と合わない。SPEC の変更が要る |
| 実装量 | renderer(パイプ・窓・描画)、TIP 側の送信 | (a) に加え、proto の変更とサーバーから renderer への接続 | 最も少ない |

## 決定

(a) にする。TIP が Output の候補と、自分で取ったキャレットの矩形(物理座標)を、renderer の名前付き
パイプへ応答を待たずに送る。renderer は受けた内容だけを描き、状態を持たない。

- (c) は仕様(REQ-10-7)と合わないので採らない。当面の代わりにする場合も SPEC の変更が要る。
- (b) は位置と中身が1キーずれるか要求が増える。サーバーに描画の都合を持ち込むことにもなる。
  利点は renderer のパイプの ACL が簡単になることだけで、(a) でもサーバーと同じ ACL の
  コード(REQ-10-4)を使い回せる。
- トランスポートは `\\.\pipe\kotori-renderer-<ユーザーSID>` にする。ACL と接続元の検証は、
  サーバーのパイプと同じ規則(REQ-10-4)に従う。renderer は TIP が最初に候補を出すときに起動し
  (サーバーと同じく単一インスタンス)、つながらなければ候補ウィンドウを出さずに入力を続ける
  (候補はプリエディットの中で切り替わる)。
- メッセージは Protocol Buffers(`kotori-proto` に `renderer.proto` を足す)で、フレームは
  サーバーと同じ「u32 の長さ + 本体」。中身は「表示(候補・注釈・選択位置・ページ・矩形・
  アプリのウィンドウ)」と「隠す」の2つ。応答は返さない。
- クリックでの選択は、TIP がアプリのスレッドに作るメッセージ専用ウィンドウへ renderer が
  `PostMessage` し、TIP が `SELECT_CANDIDATE`(カード 10)をサーバーへ送る。UIPI で届かない
  管理者のアプリでは、クリックは使えずキーだけで選ぶ。
- 位置の決め方(画面の端での移動、入力中の文字を隠さない、REQ-11-3)は、モニタの作業領域と
  矩形とウィンドウの大きさから位置を返す純粋関数にし、Linux でもテストする。

## 影響

- 実装を3枚のカードに分ける(`docs/tasks/13`〜`15`)。サーバーのパイプの ACL(REQ-10-4)は
  まだ同じユーザーだけを許していて、AppContainer と低整合性に対応していない。renderer でも
  同じ規則を使うので、先にカード 16 で直す。
- キー1回あたりの IPC が1回増える(候補ウィンドウが出ている間だけ)。応答を待たないので、
  キーの応答時間の要件(4.2 の 200ms)には影響しない。
- macOS と Linux は各 OS の UI で描く(REQ-4-3)ので、この決定は Windows だけに関わる。
