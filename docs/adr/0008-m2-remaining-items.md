# 0008: M2 の残りの扱いと M3 への移行

- 状態: 採用
- 日付: 2026-09-29

## 背景

M2(18.3)の実装項目のうち、判断なしで進められるものは PR #24〜#35 で入れた。zenz-v2.5-small の
リランクで AJIMEE-Bench Acc@1 は 53.0% から 79.5% になった。残りは次の理由で止まっている。

- REQ-6-1(リランク p95 20ms)は、今の方式とモデルの大きさでは満たせない(Issue #32)。
- 重みの調整(7.3)に使う dev セットは 7.2 のパイプラインから作る前提で、まだない。
- 完了条件の KTB-conv も 7.2 の test 分割と人手の確認が要る。
- 完了条件の Google 日本語入力との比較は、Windows 上の計測(14.2 の `kotori-imebench`)が要る。

メンテナから判断を任されたので、SPEC の変更を伴わないものをここで決める。SPEC の数値や規約を
変えるもの(REQ-6-1・13.2、17.2 の unsafe の範囲)は、承認付きの PR で別に扱う(AGENTS.md 6)。

## 決定

1. **重み**: 既定値(λ_lm=1、λ_lattice=1、T=1000)のままにする。AJIMEE-Bench での感度では最良から
   0.5 ポイント以内だった(`eval/README.md`)。zenz-v2.5-dataset はモデル自身の学習データで、
   LM のスコアが実際より高く出るので、調整には使わない。7.2 の dev セットができたら
   `kotori-eval tune` で調整する。
2. **KTB-conv**: 7.2 のパイプラインを作るとき(18.7 の自前学習の準備)に作る。それまで M2 の
   精度は AJIMEE-Bench で見る。
3. **Google 日本語入力との比較**: M3 で Windows の計測ツールを作るときに行う。
4. **REQ-6-1**: 2段階応答で進める。キー応答はラティス単体で返し(13.2 のキー応答の目標)、
   リランクの結果は後から差分更新で反映する(REQ-4-4、6-2)。そのためのエンジン側の部品
   (世代番号による打ち切り、締め切り、遅れた結果の取り出し、バックグラウンド読み込み)は
   `kotori-lm` にある。セッションへの組み込みは状態機械(11.1、11.2)と一緒に M3 で行う。
   数値の目標の変更は Issue #32 と SPEC の PR で扱う。
5. **差分更新の送り方**: IPC は要求と応答の組(4.2)なので、フロントエンドが問い合わせる形
   (差分の有無を尋ねる要求を足す)を第一案にする。サーバーからの押し付けは枠組みを変えるので
   採らない。プロトコルの変更は M3 のフロントエンドと同じ PR の流れで入れる。
6. **zenz-v2.5 の配布**: 変換した GGUF は配布しない。利用者が `just zenz` で手元で取得・変換する
   (docs/adr/0007)。
7. **辞書の mmap(Issue #9)**: 結論が出るまで `std::fs::read` で読み込み、`unsafe` は増やさない。
8. **マイルストーン**: M2 の完了条件のうち、上の理由で今は満たせないもの(REQ-6-1、KTB-conv、
   Google との比較)を残したまま、M3 に進む。残りは AGENTS.md に記録し、条件が揃ったら戻る。

## 影響

- M3 では、セッションの状態機械にラティス単体の変換とリランクの差分更新を組み込み、
  フロントエンドが差分を問い合わせる要求をプロトコルに足す。
- M2 の完了は、REQ-6-1 の扱いが決まり、KTB-conv と Google との比較がそろった時点で判定する。
